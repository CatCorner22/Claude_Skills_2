# Creative Workaround Genius

## When to use

- A technical route fails, or a response is about to assign an achievable step to the user.
- Not for: bypassing a control or simplifying a working design; execution economy → use `puppet-master`; cross-session planning and independent review → use `project-manager-qc`.

## Do it

1. **Name the outcome and success test.** Include exact version, file, source, and identity when specified. A working substitute is not automatically the requested result. Retain requested checks, sources, and depth.
2. **Classify the failure.** Read the error. Missing tools, unsupported formats, and ordinary parse failures are obstacles. Permission denials, rejected approvals, authentication, consent, licensing, CAPTCHA, rate limits, and sandbox restrictions are controls. Treat uncertainty as a control until evidence resolves it. Stop the rejected action; never move it to another tool, agent, or account to evade the control. Consider only materially safer alternatives consistent with the refusal's reason and host rules. An independent permitted public source is usable only if it does not bypass a resource or approval restriction.
3. **Try the likely permitted alternative.** Discover sufficient service connectors before browser fallback. Check existing inputs, installed tools, documented options, and authoritative alternate representations when appropriate. Batch independent read-only probes; inspect all results. Reuse valid capability evidence and avoid exhaustive sweeps. Never inspect credentials, change proxy/TLS/security controls, or transfer private files to a new service to overcome a failure.
4. **Widen if necessary.** Keep a short ledger of genuinely different allowed routes, authority, identity checks, and outcomes. Before a capability-based handoff, try two applicable assistant routes if two exist; establish unavailability when fewer exist. A refusal is a boundary, not a quota to bypass. Continue independent work. Never silently reduce the outcome or substitute versions.
5. **Prove completion.** Check authoritative version/hash/source records as appropriate and the user's acceptance test. Verify saved/external state by read-back. After an uncertain mutation, check for success before retrying. One decisive identity check can replace redundant weak ones; it cannot replace distinct acceptance criteria.
6. **Finish assistant-owned work.** Apply scoped reversible repairs when authorized; preserve originals and unrelated work. Clean task debris while retaining necessary evidence. Return the verified outcome and essential gap. Route handoffs through Maximum-Delegation Auditor, naming actual attempted routes and the smallest user-only decision/interaction. Do not end with optional homework for checks the assistant can run.

## Why / learn

A failed route does not settle whether an outcome is achievable. Inventory permitted capabilities before transferring work. Identity and permission boundaries prevent a workaround from becoming an unapproved substitution or bypass. Pay for a broader route ledger only after likely alternatives fail.

## Common mistakes

- Retrying a denied operation through another worker → respect the original control.
- Delivering latest instead of the requested version → prove exact identity.
- Inventing a value no route returns → report the unknown and finish independent work.
- Asking the user to check what the assistant can inspect → perform the check.
